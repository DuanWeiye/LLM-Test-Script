# 纯裸测 `bare_llm/`

直连任意 **OpenAI 兼容** `/chat/completions` 端点，考模型**自己会什么** —— 不给工具、不给
脚手架、不给文件系统，一问一答（多轮卷除外）。与 [`agent/`](../agent/) 那套互补：
那边考「把活交给它能不能干成」，这边考「它自己肚子里有多少」。

```bash
export LLM_BASE_URL="http://你的地址:端口/v1"   # 默认 http://127.0.0.1:12345/v1

cd bare_llm
# 参数1 = 逗号分隔的模型名（须是端点认识的 model id）；参数2 = 结果文件标签（可选）
python3 full_eval.py      "my-model-a,my-model-b"  run1
python3 full_eval_hard.py "my-model-a,my-model-b"  run1
```

- 客观项（编码执行、工具 schema、关键词/格式）**自动判分**并打印。
- 主观项（幻觉诚实度、代码质量、翻译/摘要忠实度）收集到 `ab_judge_queue*.json`，
  **留给人或更强的模型盲评** —— 脚本不替你判主观题。
- 结果写 `ab_results<标签>.json`。出汇总表用仓库根的 `make_report.py`。

对端点的要求：工具题需要端点支持 OpenAI `tools` 参数与 `tool_calls` 返回。

**模型写的代码在容器里跑**：`run_code()` / `run_code_verdict()` 执行的是模型现写的
Python，默认放进 `llm-eval-agent` 镜像（`--network none`、只读根 fs、只挂一个临时目录）。
`EVAL_CODE_SANDBOX=auto|docker|host` 可切，开跑会打印当前档位。详见
[`agent/DESIGN.md`](../agent/DESIGN.md) 〇之二节。

## 主卷 / 回归卷

2026-09-06 起裸卷分成两档。起因是随着模型变强，八个维度里有五个已经**全模型接近满分**
—— 约 150/342 分变成死分，只会稀释真正的差距。

| | 维度 | 用途 |
|---|---|---|
| **主卷** | 高难算法(X) · 工具判断 · 多约束指令 · **多轮一致性** · **长上下文推理** · **约束冲突** | **选型只看这个** |
| **回归卷** | 基础算法(HC) · 编码(三语) · 事实 · 格式 · 多步推理 · 知识广度 · 多轮基本功 | 题照跑，但只用来**发现退步** |

加粗的三个是 2026-09-06 新增的，各补一个此前完全测不到的盲区：

| 卷 | 文件 | 补的是什么盲区 |
|---|---|---|
| 多轮一致性 MT1~4 | `cases_multi.py` | 改版前**裸卷 100% 是单轮题**，长对话里约定守不守、事实记不记得、改主意跟不跟得上，全都测不到 |
| 长上下文推理 LR1~4 | `cases_longctx.py` | 接替已饱和的 NIAH。**光捞出来没用，得把几条组合起来才能作答**（两跳/三跳+算/变量追踪/后文修正），默认 128K |
| 约束冲突 IFC1~4 | `cases_conflict.py` | 用户提的要求里**本身就有矛盾**时认不认得出来。★含一道**无冲突对照组**，误报同样算错 —— 否则模型见到长约束列表就喊「有冲突」即可满分 |

> ⚠ 约束冲突这一卷**要看题级结果，别只看维度均值**：IFC1 与 IFC3 的方向是相反的
> （27b 在 IFC1 上 3/3、35b 在 IFC3 上 2/3），平均下来两个模型都是五成，信号被抵消。

饱和的题**不删** —— 新模型要是在基本功上掉下来，仍然要能立刻看见。

### 入卷标准：看模型之间拉不拉得开

新题必须先拿**一强一弱两个模型**实测：

| 实测结果 | 归属 |
|---|---|
| 所有模型都接近满分 | 回归卷（饱和） |
| 所有模型都接近全灭 | 废题，要改造 |
| 模型之间拉得开 | **主卷**，哪怕某个模型是 0/3 |

> ⚠ 这条标准最初写的是「最弱模型通过率落在 30~70%」，落地当天就被打脸：
> 长上下文题 LR3 在 `qwen3.6-35b-a3b` 上 **0/3**、在 `qwen3.8-27b` 上 **3/3**，
> 按旧标准会被当成「太难」剔掉 —— 可它恰恰是全卷最干净的区分器。
> **单个模型的绝对通过率不是难度，模型之间的差距才是。**

**判难度之前先排除判分器和截断**：MT4 最初实测 0/3，查下来是 `max_tokens` 把回复截断、
围栏不闭合、判分器退化成「整段散文当代码」，于是模型在正文里写「不要用 `eval()`」
也被判违规 —— 是判分 bug，不是题难。修完变成 1/3。**「全灭」第一反应应该是查判分器。**

## 采样口径与噪声

**不指定任何采样参数**，由端点按各模型自己的官方推荐设定跑（llama.cpp 系在启动参数里配
`--temp/--top-p/--top-k`，云端 API 不传即用官方默认）。

温度 0 的贪心解码虽然确定性好，但偏离多数模型的 `generation_config`（明确 `do_sample=true`），
属于「没按说明书用」—— 对经 RL 对齐的模型可能系统性低估，有些模型在温度 0 下甚至无法正常工作。
代价是结果带采样方差，所以**每道题默认跑 3 次**（`EVAL_REPEAT` 可调），成绩记成「过了几次/3」。
想复现温度 0 的贪心对照：`EVAL_TEMPERATURE=0 EVAL_REPEAT=1`。

### 想把噪声压下去：跑第二轮独立采样

3 次/题在**比较两个相近配置**时分辨率不够 —— 同一个配置重跑，总分能差 5 分。
seed 默认是 `1..EVAL_REPEAT`；设 **`EVAL_SEED_BASE`** 就能拿到不重叠的下一段 seed：

```bash
python3 full_eval.py "my-model" run1                    # seed 1,2,3
EVAL_SEED_BASE=3 python3 full_eval.py "my-model" run2   # seed 4,5,6
```

两轮结果合并成 6 次/题：`make_report.py` 里 `MODEL_TAG` 的值写成**标签列表**
（`"my-model": ["run1", "run2"]`），报告按题累加 `pass`/`n`，表里如实显示 `x/6`，
百分比仍可与 3 次的那些列横比。

比较两个配置时的建议流程：**每格都跑两轮 → 先看轮内波动有多大（那就是噪声底）→
再看格间差是否明显大于它**。没有这一步，几分的总分差只能说「在噪声内」。

思考模型另有两个坑：reasoning 也占 `max_tokens` 预算，用给非思考模型定的紧预算测思考模型
会大量假性截断 —— 用 `EVAL_MAX_TOKENS_MIN` / `EVAL_MAX_TOKENS_MULT` 放宽，
并把 `EVAL_HTTP_TIMEOUT` 一起调大，否则截断和超时会被当成答错。

## 超长上下文大海捞针 `niah_full.py`（★已退役）

**2026-09-06 起不再作为选型依据**：全部模型在 4 个长度档 × 6 个深度上**全部 6/6 命中**，
零区分度 —— 纯检索式的捞针对现在这批模型不构成挑战了。脚本保留（`niah_lib.py` 的造长文
基建可直接复用），要测长上下文能力请用主卷的 LR1~LR4 那种**必须组合多处信息**才能作答的题。

```bash
python3 niah_full.py "my-model-a,my-model-b"     # 结果写 niah_results.json
```

在一篇塞满**同款干扰项**的长文里埋 6 个不同深度（5%–95%）的「针」，4 个长度档
（8K/64K/160K/224K token）各问一遍。依赖返回体里的 `timings.prompt_n` 与 `cache_prompt`
（llama.cpp 系有）；其它引擎没有也能跑，只是拿不到 prefill 统计、长文会更慢。

## 文件

| 文件 | 是什么 |
|---|---|
| `eval_lib.py` | 公共库：发请求、多轮 `chat_turns`、各类自动判分器、代码执行沙箱、工具集 |
| `full_eval.py` | 常规卷：编码 / 工具 / 事实幻觉 / 格式 / 三语 |
| `full_eval_hard.py` | 难卷：硬算法 / 多步推理 / 更广知识 / 多约束指令 / 更难工具 |
| `cases_multi.py` | 多轮一致性 MT1~MT4 |
| `cases_longctx.py` | 长上下文推理 LR1~LR4 |
| `cases_conflict.py` | 约束冲突 IFC1~IFC4 |
| `cases_hard.py` | 难卷题库（硬算法 HC / X 等） |
| `niah_lib.py` / `niah_full.py` | NIAH 造文基建与跑法（已退役） |
| `verdict.py` | F2P / P2P 计分对象 |
