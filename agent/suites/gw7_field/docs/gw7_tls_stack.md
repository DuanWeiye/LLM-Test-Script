# GW-7 内置 TLS 子系统说明（固件 3.x）

> 面向集成商，讲的是网关里那套精简 TLS 实现的资源约束。和标准 OpenSSL 行为**不一样**，
> 移植上层程序时最容易踩的就是这一节。

## 会话槽位表（session slot table）

为了在 64MB RAM 的机型上也能跑，TLS 子系统把每条连接的收发缓冲、握手上下文、
会话票据打包成一个「槽位」，整机**静态分配 8 个**（`GW7_TLS_MAX_SESSIONS`，编译期常量，
运行时不可调；3.x 全系列都是 8）。

- 握手成功 = 占用一个槽位，日志打 `handshake ok ... in_use=n/8`
- 槽位用满之后，任何新的握手直接被拒，错误码固定是
  **`no buffer available`** —— 这个报错的字面意思很有误导性，它说的**不是内存不够**，
  而是槽位表满了。整机内存可能还剩几百 MB。

## 槽位什么时候才释放

**只有收到对端的 `close_notify`（TLS 层的正常关闭告警）才会释放槽位。**

这是这套实现最容易出事的地方：

- 上层直接 `close(fd)` / 进程退出 / 连接被 abort —— TCP 层是断了，但 TLS 子系统
  收不到 `close_notify`，会认为这条会话「还可能续用」，把槽位**继续占着**，
  日志打 `peer socket gone, no close_notify received ... (slot retained)`。
- 被 retain 的槽位**没有超时回收**。3.x 没有实现槽位 GC，issue 里挂了很久没做。

也就是说：每一条没有正常关闭的连接，就永久漏掉一个槽位。漏满 8 个，
上报就彻底断了，而且**不会自己恢复**。

## 怎么恢复

- **立刻恢复**：重启 TLS 子系统即可，不必重启整机 ——
  `gw7ctl restart tls`（会顺带断开当时所有连接），槽位表清零。整机重启当然也行。
- 3.x 没有单独释放某个槽位的命令。`gw7ctl tls status` 可以看当前 `in_use`。

## 怎么写才不会漏

1. **复用连接**：批量传输走同一条 keep-alive 连接，别一批开一堆。
2. **一定要正常关闭**：发完调库的 `gw7_tls_close()`（它会发 `close_notify`），
   不要直接关 socket，也不要靠进程退出去「顺便」关。
3. **并发上限**：真的要并发，把并发数压到**小于 8**，并且给每条连接做正常关闭；
   否则一次批量就能把槽位表打满。

## 运维上的权宜之计

在改不动上层程序的场合，常见做法是：批量任务跑完之后主动 `gw7ctl restart tls`
把槽位清一次，或者干脆挂个定时任务每天重启一次 TLS 子系统。
这不解决漏槽位本身，只是把它摊掉。
