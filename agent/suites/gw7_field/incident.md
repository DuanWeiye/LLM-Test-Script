# 现场故障单 · GW-7 边缘网关批量上报后失联

- 单号：INC-2026-0730-014
- 报单人：值班（现场只能远程看日志，设备在客户机房，短期拿不回来）
- 影响：12 台里有 9 台出现，剩下 3 台没开夜间批量上报

## 现象

1. 白天一切正常，每 5 分钟一次的定时上报连续几百次没问题。
2. **凌晨 02:00 的夜间批量补传跑完之后**，接下来的定时上报开始一条都传不上去。
3. 失败一直持续，不会自己好。设备本身没死机 —— SSH 进得去，采集还在写本地库，
   只是上报全挂。
4. 只要把设备重启，立刻恢复正常，然后又能撑到第二天凌晨。

## 上报侧报错

```
02:03:11 upload  ERR  post /v2/batch failed: tls handshake failed (no buffer available)
02:08:00 upload  ERR  post /v2/points failed: tls handshake failed (no buffer available)
02:13:00 upload  ERR  post /v2/points failed: tls handshake failed (no buffer available)
...（此后每 5 分钟一条，一模一样）
```

## 已经排除的

- **不是网络**：同一时刻 `ping` 上报域名 3ms 无丢包；`curl -v https://<上报域名>/healthz`
  从**同一台设备**上跑是通的（返回 200）。DNS 解析正常。
- **不是服务端**：服务端访问日志里根本没有这些失败请求的记录，说明连接压根没建起来。
  同机房另一台没跑批量补传的 GW-7 一直正常上报。
- **不是内存**：`free` 显示可用内存 700MB 以上，故障前后没有明显变化，dmesg 无 OOM。
- **不是磁盘**：`df` 还有 60% 空间，本地库写入正常。
- **不是证书过期**：证书还有 60 天，且重启后用同一张证书就能连上。

## 现场能拿到的东西

- `logs/upload.log` —— 上报模块日志（含故障前后）
- `logs/tlsmon.log` —— TLS 子系统自己打的状态日志
- `docs/` —— 客户给的这批设备的技术资料（如果这次现场发下来了的话）
